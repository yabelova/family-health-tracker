# Family Health Tracker

Telegram-бот для контроля планов лечения и учёта медикаментов с функцией совместного управления профилями
(например, два родителя ведут профиль ребёнка).

## Стек

Java 25, Spring Boot, Spring Data JDBC, PostgreSQL, Flyway, TelegramBots.

## Запуск

1. Создайте файл `.env` на основе `docker-compose.yml` (переменные `DB_USER`, `DB_PASSWORD`, `DB_NAME`,
   `DB_HOST`, `DB_PORT`, `TELEGRAM_BOT_NAME`, `TELEGRAM_BOT_TOKEN`).
2. Запустите БД: `docker compose up -d`.
3. Приложение поднимет схемы через Flyway автоматически.

## Архитектура

Проект разделён на четыре слоя:

* **domain** — сущности предметной области (`Profile`, `User`, `UserRole`).
* **repository** — доступ к данным (Spring Data JDBC), Flyway-миграции.
* **service** — бизнес-логика, Telegram-free и юнит-тестируемая
  (`UserService`, `ProfileService`, `NotificationService`).
* **telegram** — UI-слой бота. Общается только с сервисами (не с репозиториями):
  * `HealthTrackerBot` — тонкий: получает `Update` и передаёт в диспетчер.
  * `BotDispatcher` — маршрутизирует ввод к командам по явным ключам (детерминированно);
    после клика съедает inline-клавиатуру сообщения (кнопки одноразовые).
  * `command/*` — команды. Каждая команда: `StartCommand`, `SelectProfileCommand`,
    `CreateProfileCommand`, `AddProfileCommand`, `ProfileMenuCommand`, `ProfileManageCommand`,
    `NotificationsCommand`.
  * `screen/*` — переиспользуемые экраны (меню профиля, выбор профиля, уведомления).
  * `support/ReplySender` — единственная точка отправки ответов в Telegram.
  * `support/KeyboardFactory` — построение reply- и inline-клавиатур.

### Паттерны

* **Command** — каждый вход (команда/кнопка) обрабатывается отдельным классом `BotCommand`;
  методы интерфейса — no-op по умолчанию (ISP): команда реализует только используемые.
* **State** — текущее состояние диалога хранится в памяти (`BotDispatcher.awaitingInput`),
  экран (меню профиля / выбор профиля) выводится из доменного контекста (`active_profile_id`).
* **Builder** — построение клавиатур и ответов через встроенные builder'ы Telegram API.

## Карта переходов (стейт-машина)

Экран определяется доменным контекстом (выбран ли профиль) + текущим ожиданием ввода (в памяти).
Reply-панель меняется в зависимости от контекста: «Меню профиля» доступно только при выбранном профиле,
«Уведомления» и «Выбор профиля» — всегда.

```
[/start]
   │
   ├─ профиль НЕ выбран ──► [ВЫБОР ПРОФИЛЯ]
   └─ профиль выбран ─────► [МЕНЮ ПРОФИЛЯ]

[ВЫБОР ПРОФИЛЯ]              (reply: 👤 Выбор профиля, 🔔 Уведомления)
   │  inline: profile.activate:1   ──► отметить is_active в tr_user_profile ──► [МЕНЮ ПРОФИЛЯ]
   │  inline: profile.create     ──► ввод имени ──► создать+выбрать ──► [МЕНЮ ПРОФИЛЯ]
   │  inline: profile.add        ──► ввод кода ──► claimInvite ──► связь MEMBER, is_active=false ──► (этот же экран)
   │  reply: 🔔 Уведомления      ──► [УВЕДОМЛЕНИЯ]
   │  reply: 👤 Выбор профиля    ──► (рендер этого же экрана)

[МЕНЮ ПРОФИЛЯ]               (reply: 📋 Меню профиля, 🔔 Уведомления, 👤 Выбор профиля)
   │  inline-действия (каркас): 💊 Принять / 📋 План / 📝 Симптом
   │  inline: profile.manage   ──► [УПРАВЛЕНИЕ ПРОФИЛЕМ] (кнопка только у владельца)
   │  reply: 🔔 Уведомления      ──► [УВЕДОМЛЕНИЯ]
   │  reply: 👤 Выбор профиля    ──► [ВЫБОР ПРОФИЛЯ]
   │  (без профиля)             ──► подсказка «Сначала выберите профиль»

[УПРАВЛЕНИЕ ПРОФИЛЕМ]         (только владелец; навигация — reply: 📋 Меню профиля)
   │  inline: profile.share    ──► создать код (8 симв., 72 ч, одноразовый) ──► показать ──► (этот же экран)
   │  inline: profile.rename   ──► ввод имени ──► переименовать ──► (этот же экран)
   │  inline: profile.revoke   ──► удалить связи MEMBER + неиспользованные коды ──► (этот же экран)
   │  inline: profile.delete   ──► ввод слова «удалить» ──► удалить ──► [ВЫБОР ПРОФИЛЯ]
   │                            ──► любой другой текст ──► отмена ──► (этот же экран)

[УВЕДОМЛЕНИЯ]                (доступен всегда)
   │  inline: notification.edit    ──► ввод ЧЧ:ММ ──► сохранить notification_time ──► [УВЕДОМЛЕНИЯ]
   │  inline: notification.disable ──► сбросить notification_time ──► [УВЕДОМЛЕНИЯ]
   │  reply: 👤 Выбор профиля      ──► [ВЫБОР ПРОФИЛЯ]
   │  reply: 📋 Меню профиля       ──► [МЕНЮ ПРОФИЛЯ] (если профиль выбран)
```

### Ожидание ввода

Одношаговые анкеты (имя профиля, время уведомлений, код приглашения, новое имя, слово подтверждения)
хранятся в памяти как `Map<chatId, AwaitingRequest(command, marker)>` в `BotDispatcher.awaitingInput`.
Маркер возвращает сама команда: когда она решает ждать следующий текст, то отдаёт ярлык этого ожидания
(например, префикс callback-действия), диспетчер лишь хранит его и передаёт обратно в `handlePendingText`.
Так одна команда может вести несколько флоу (например, переименование и удаление профиля) и различать их,
а многошаговая анкета возвращает следующий шаг как новый маркер. Контракт возврата: `null` — анкета
завершена; не-`null` — ожидание продолжается под этим маркером. Любая навигация (reply-кнопки, другие
callback) сразу снимает ожидание — флоу «умирает».

## База данных

| Таблица | Назначение |
|---|---|
| `t_users` | пользователи бота (`notification_time`) |
| `t_profiles` | профили (подопечные) |
| `tr_user_profile` | связь пользователь ↔ профиль (роль OWNER/MEMBER, `is_active` — активный профиль; уникальный частичный индекс гарантирует один активный на пользователя) |
| `t_profile_invites` | одноразовые коды приглашений (8 символов, TTL 72 ч, атомарный claim в `claimInvite`) |

Миграции: `src/main/resources/db/migration`.
