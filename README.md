# Family Health Tracker

Telegram-бот для контроля планов лечения и учёта медикаментов с функцией совместного управления профилями (например, два
родителя ведут профиль ребёнка).

## Стек

Java 25 (виртуальные потоки), Gradle, Spring Boot (Spring Data JDBC), PostgreSQL, Flyway, TelegramBots (long polling),
Lombok.

## Запуск

1. Создайте файл `.env` на основе `docker-compose.yml` (переменные `DB_USER`, `DB_PASSWORD`, `DB_NAME`, `DB_HOST`,
   `DB_PORT`, `TELEGRAM_BOT_NAME`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ALLOWED_IDS`).

### Через Docker (весь стек)

2. БД + приложение: `docker compose up --build -d` (Flyway поднимет схемы автоматически).
3. Логи: `docker compose logs -f app`.
4. Версия приложения (из `build.gradle.kts`) видна в логах и через актуатор: `curl http://localhost:8080/actuator/info`.

### Для локальной разработки

2. БД: `docker compose up -d health_tracker_db`.
3. Приложение: `gradlew.bat bootRun --args='--spring.profiles.active=local'` (профиль включает SQL-логирование
   `JdbcTemplate: TRACE`, конфиг `application-local.yaml`).

Схемы БД поднимаются Flyway автоматически при первом старте приложения.

Бот отвечает только telegram-идентификаторам из `TELEGRAM_ALLOWED_IDS` (пустой список закрывает бота).

## Тесты

`gradlew.bat test` — юнит- и интеграционные тесты (Testcontainers); интеграционные используютодноразовый PostgreSQL в
Docker и требуют запущенного Docker.

## Приватность и безопасность

* В БД хранятся следующие данные: информация, которую пользователь вносит сам (профили, записи по профилям, настройки
  уведомлений), и сведения из Telegram: `telegram_id` (в личном чате с ботом совпадает с id чата), имя, username.
* Логи обезличены: текст сообщений не пишется — только `telegram_id`, тип ввода (текст/callback), длина текста и команда
  (для кнопок).
* Секреты задаются через `.env` и в репозиторий не попадают.
* Бот отвечает только telegram-идентификаторам из `TELEGRAM_ALLOWED_IDS` (пустой список закрывает его полностью).
* Управление профилем (шеринг, смена владельца, удаление) может выполнять только владелец; доступ проверяется в момент
  операции. При удалении профиля все его записи удаляются вместе с ним. Общий профиль удалить напрямую нельзя — только
  передав владение или отозвав доступ. Конфликт записи и отзыва прав или удаления профиля решается pessimistic lock:
  начавшаяся первой операция действует, вторая дожидается её завершения.
* `/delete_all_data` — полное удаление аккаунта из бота: данные профилей удаляются по правилам выше, и пользователь
  удаляется из системы.

## Архитектура

Проект разделён на четыре слоя:

* **domain** — сущности предметной области (`Profile`, `User`, `MedicationCourse`, `MedicationIntake`,
  `SymptomLog`, ...) и классы свойств для форм визардов.
* **repository** — доступ к данным (Spring Data JDBC; `ProfileRepository`, `MedicationCourseRepository`, ...);
  конвертеры типов БД ↔ свойства анкет — `config/converter`; Flyway-миграции — в `resources/db/migration`.
* **service** — бизнес-логика, Telegram-free и юнит-тестируемая (`ProfileService`, `NotificationService`,
  `IntakeService`, `MedicationCourseService`, ...).
* **telegram** — UI-слой бота:
    * `HealthTrackerBot` — тонкий: получает `Update` и передаёт в `UpdateHandler`.
    * `UpdateHandler` — интерфейс обработки входящего апдейта.
    * `PerChatUpdateHandler` — декоратор над `BotDispatcher` (режим по умолчанию): очередь на каждый чат, апдейты одного
      чата последовательны (виртуальный поток `task-chat-<id>`), разные чаты — параллельны. Отключается флагом
      `app.parallel.enabled=false`.
    * `BotDispatcher` — маршрутизирует ввод к командам по явным ключам (детерминированно); после клика уничтожает
      inline-клавиатуру сообщения (кнопки одноразовые); карты команд immutable, `awaitingInput` — потокобезопасный.
    * `command/*` — команды: старт, профили (выбор/создание/шеринг/управление), уведомления, приватность, помощь;
      `command/section/*` — разделы записей (симптомы, курсы, приёмы) на `AbstractSectionCommand` (меню, выгрузка,
      удаление по id, шапка «Профиль: имя»); `command/wizard/*` — визарды анкет (симптом, курс) на
      `AbstractWizardCommand` (шаги рефлексией из класса свойств, подтверждение/отмена кнопками); `command/intake/*` —
      флоу отметки приёма (не визард): `IntakeTakeCommand` + `IntakeFlowMarker`, шаги препарат → дозы → время →
      подтверждение.
    * `scheduler/NotificationScheduler` — ежедневная рассылка планов на сегодня (@Scheduled).
    * `screen/*` — переиспользуемые экраны (меню профиля, выбор профиля, уведомления).
    * `support/*` — `ReplySender` (единственная точка отправки ответов в Telegram), `KeyboardFactory` (reply- и
      inline-клавиатуры), `DailyPlanFormatter` (HTML-текст плана на сегодня), `BotTexts`, `Commands`,
      `ConfirmationWords` (все пользовательские тексты и токены).

Вне четырёх слоёв лежат вспомогательные пакеты: `wizard` — переиспользуемый движок визардов (шаги, валидация, рефлексия
форм), который используют визарды команд и разметка форм в domain; `config` — конфигурация Spring и бинов; `exception` —
предметные исключения и тексты ошибок (`ErrorTexts`); `util` — утилиты (время, числа, даты).

### Паттерны

* **Command** — каждый тип входа (текстовая команда, reply-кнопка, inline-кнопка) обрабатывается отдельным
  классом-командой интерфейса `BotCommand`; диспетчер маршрутизирует по ключам, объявленным командой (no-op по
  умолчанию, ISP).
* **Template Method** — `AbstractSectionCommand` и `AbstractWizardCommand` задают скелет сценария (меню раздела, шаги
  анкеты с подтверждением/отменой), потомки реализуют только вариативные части (заголовок, превью, поля формы).
* **State** — состояние диалога живёт в маркере флоу, а не в потоке: поток может меняться между апдейтами чата, а анкета
  продолжается под тем же маркером.
* **Decorator** — `PerChatUpdateHandler` поверх `BotDispatcher` добавляет per-chat очередь и виртуальный поток на чат.
* **Builder** — клавиатуры и ответы — builder'ами Telegram API, сборка сущностей — Lombok `@Builder`.

DI и Repository — стандартные механизмы Spring.

### Параллелизм

Каждый чат обрабатывается в виртуальном потоке с собственной очередью: апдейты одного чата последовательны, разные
чаты — параллельно. Весь ввод передаётся в `PerChatUpdateHandler`.

Флаг `app.parallel.enabled=false` отключает параллелизм и возвращает синхронную обработку напрямую `BotDispatcher`.

Для проверки параллелизма вживую есть временная демо-команда `/sleep` — она засыпает в потоке своего чата, остальные
чаты продолжают отвечать. Демо включается и отключается флагом `app.demo.sleep.enabled` в `application.yaml`
(длительность — `app.demo.sleep.seconds`). Для сравнения: с `app.parallel.enabled=false` тот же `/sleep` блокирует все
чаты.

Блокировок в памяти нет: апдейты одного чата последовательны (своя очередь + виртуальный поток), между чатами общего
изменяемого состояния нет, ожидаемый ввод — потокобезопасная `ConcurrentHashMap`. Там, где нужна синхронизация между
операциями одного профиля (запись против отзыва прав или удаления профиля), её выполняет БД pessimistic-lock на строке
связи (`SELECT ... FOR UPDATE`): начавшаяся первой операция действует, вторая дожидается завершения.

## Карта переходов (стейт-машина)

Экран определяется доменным контекстом (выбран ли профиль) + текущим ожиданием ввода (в памяти). Ожидание ввода —
маркер, возвращаемый командой (null — анкета завершена); reply-кнопка меню или callback другой команды снимает его.

Reply-панель (2×2) фиксированная: «Меню профиля», «Выбор профиля», «Уведомления», «Помощь». Рисуется один раз на
`/start` и экранами не перерисовывается — Telegram хранит её сам.

```
[/start]                     (вход — telegram_id из TELEGRAM_ALLOWED_IDS)
   ├─ юзер не из whitelist  ──► сообщение о запрете доступа один раз на чат, команды недоступны
   │
   ├─ профиль НЕ выбран     ──► [ВЫБОР ПРОФИЛЯ]
   └─ профиль выбран        ──► [МЕНЮ ПРОФИЛЯ]

[ВЫБОР ПРОФИЛЯ]              (доступен всегда)
   │  выбрать профиль       ──► отметить is_active в tr_user_profile ──► [МЕНЮ ПРОФИЛЯ]
   │  создать профиль       ──► ввод имени ──► создать + выбрать ──► [МЕНЮ ПРОФИЛЯ]
   │  добавить по коду      ──► ввод кода ──► claimInvite ──► связь MEMBER (is_active=false) ──► (этот же экран)

[МЕНЮ ПРОФИЛЯ]               (доступен всегда при наличии выбранного профиля)
   │  управление профилем   ──► [УПРАВЛЕНИЕ ПРОФИЛЕМ] (кнопка только у владельца)
   │  симптомы/курсы/приёмы ──► [РАЗДЕЛ ЗАПИСЕЙ] (любой участник профиля)
   │  (без профиля)         ──► [ВЫБОР ПРОФИЛЯ]

[РАЗДЕЛ ЗАПИСЕЙ]             (симптомы / курсы / приёмы)
   │  добавить              ──► визард анкеты (шаги ──► подтвердить/отменить) ──► [РАЗДЕЛ ЗАПИСЕЙ]
   │  отметить приём        ──► визард-анкета (препарат ──► дозы ──► время ──► подтверждение;
   │                            дубль — «Уже отмечено», перерасход — «Не хватает доз») ──► [РАЗДЕЛ ЗАПИСЕЙ]
   │  выгрузить             ──► симптомы — за 7 дней; курсы — активные и недавно завершённые,
   │                            остаток доз; приёмы — за 7 дней по дате приёма
   │  удалить               ──► список записей кнопками по id ──► перерисовать список
   │  назад                 ──► [МЕНЮ ПРОФИЛЯ]
   │  (доступ отозван)      ──► «К профилю нет доступа» ──► [ВЫБОР ПРОФИЛЯ]

[УПРАВЛЕНИЕ ПРОФИЛЕМ]        (только владелец)
   │  в меню профиля        ──► [МЕНЮ ПРОФИЛЯ]
   │  поделиться профилем   ──► создать код (8 симв., 72 ч, одноразовый) ──► (этот же экран)
   │  переименовать         ──► ввод имени ──► (этот же экран)
   │  отозвать доступ       ──► удалить связи MEMBER и неиспользованные коды ──► (этот же экран)
   │  передать владение     ──► список участников ──► ввод «передать» ──► передача ролей ──► [ВЫБОР ПРОФИЛЯ]
   │                            иначе ──► отмена ──► (этот же экран)
   │  удалить профиль       ──► ввод «удалить» ──► удалить ──► [ВЫБОР ПРОФИЛЯ]
   │                            иначе ──► отмена ──► (этот же экран)

[УВЕДОМЛЕНИЯ]                (доступен всегда)
   │  изменить время        ──► ввод ЧЧ:ММ ──► (этот же экран)
   │  отключить             ──► выключить рассылку плана ──► (этот же экран)
   │  «План на сегодня»     ──► вывести план (тот же текст, что при рассылке;
   │                            пометку «отправлено» НЕ ставит) + кнопка «↩️ Назад» ──► [УВЕДОМЛЕНИЯ]
   │  (планировщик)         ──► запуск раз в минуту: поиск юзеров, ожидающих ежедневный план;
   │                            сборка и отправка плана по профилям

[ПОМОЩЬ]                     (доступен всегда)
   │  «Помощь» / /help      ──► справочный текст (без смены экрана)

[/delete_all_data]           (двухфазное атомарное удаление аккаунта)
   │  предупреждение + классификация профилей:
   │     • личные — будут удалены
   │     • member — выход из профиля
   │     • общие (владелец) — по одному меню: передать владение / отозвать доступ
   │  после всех решений    ──► сводка плана удаления
   │  ввод «удалить»        ──► один @Transactional (передачи/отзывы ──► каскад удаления)
   │  любой другой текст    ──► отмена, данные неизменны
```

## Уведомления

### Сценарий 1 — ежедневный «План на сегодня»

Ежеминутный тик (`NotificationScheduler`, cron `0 * * * * *`) выбирает пользователей, у которых `notification_time`
наступила, а `last_notified_date` ещё не сегодня, и высылает активные на сегодня курсы по профилям (профили без
активных курсов пропускаются).

* Пометка `last_notified_date = today` — после подтверждённой отправки; потеря доставки догонит следующий тик.
* Сбой одного пользователя не роняет тик: обработка per-user.
* Пустой день — не шлём, но помечаем `last_notified_date = today` (иначе тик переспрашивал бы каждую минуту); при смене
  дня пометка устаревает сама (т.к. сравнение по дате).
* При установке времени уведомления: если новое время впереди - план придёт сегодня; наступило или ровно сейчас - начнём
  с завтра.
* Ручная кнопка «План на сегодня» показывает тот же текст.
* Время уведомлений в МСК таймзоне (константа в `TimeZones`).

### Сценарий 2 — «заканчивается лекарство»

При отметке приёма, когда курс входит в нижнюю зону (`dosesPerPackage − dosesTaken ≤ dosesPerDay`, без нормы — порог 1),
участники профиля (кроме отметившего приём) получают предупреждение. Срабатывает только при пересечении границы сверху:
повторный приём в той же зоне и перерасход молчат.

## База данных

| Таблица                | Тип связи                                             | Назначение                                                                                                              |
|------------------------|-------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------|
| `t_users`              | -                                                     | пользователи Telegram: `telegram_id` уникален; `notification_time`/`last_notified_date` — настройка и дедуп рассылки    |
| `t_profiles`           | -                                                     | профили (подопечные)                                                                                                    |
| `tr_user_profile`      | M:N `t_users` ↔ `t_profiles`                          | связь пользователь ↔ профиль (роль OWNER/MEMBER; активный профиль — один на пользователя)                               |
| `t_profile_invites`    | N:1 → `t_profiles`, `t_users`                         | коды приглашений (8 символов, TTL 72 ч, одноразовые)                                                                    |
| `t_symptom_logs`       | N:1 → `t_profiles`, `t_users`                         | записи симптомов (jsonb `properties`)                                                                                   |
| `t_medication_courses` | N:1 → `t_profiles`, `t_users`                         | курсы лечения (jsonb `properties`; `doses_taken` — счётчик принятых доз)                                                |
| `t_medication_intakes` | N:1 → `t_profiles`, `t_medication_courses`, `t_users` | приёмы лекарств (jsonb `properties`; `course_id` — справочно; индекс `uq_med_intake_dedup` защищает от двойной отметки) |

Связи поддерживаются внешними ключами: данные профиля удаляются каскадом, автор записи и курс приёма обнуляются
(`ON DELETE SET NULL`).

Миграции (Flyway): `src/main/resources/db/migration`.
