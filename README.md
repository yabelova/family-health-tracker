# Family Health Tracker

Telegram-бот для контроля планов лечения и учёта медикаментов с функцией совместного управления профилями (например, два
родителя ведут профиль ребёнка).

## Стек

Java 25 (виртуальные потоки), Gradle, Spring Boot (Spring Data JDBC), PostgreSQL, Flyway, TelegramBots, Lombok.

## Запуск

1. Создайте файл `.env` на основе `docker-compose.yml` (переменные `DB_USER`, `DB_PASSWORD`, `DB_NAME`,
   `DB_HOST`, `DB_PORT`, `TELEGRAM_BOT_NAME`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ALLOWED_IDS`).
2. Запустите БД: `docker compose up -d`.
3. Приложение поднимет схемы через Flyway автоматически.

Для локальной разработки SQL-логирования (`JdbcTemplate: TRACE`) есть профиль `local`:
`gradlew.bat bootRun --args='--spring.profiles.active=local'` (конфиг — `application-local.yaml`).

Бот отвечает только telegram-идентификаторам из `TELEGRAM_ALLOWED_IDS` (список id через запятую);
пустой список полностью закрывает бота.

## Приватность и безопасность

* Бот хранит только данные, которые вносит пользователь: профили и настройки уведомлений.
* Логи бота обезличены: без текста сообщений — только тип ввода (текст/callback), его длина и
  служебные маркеры флоу; данные пользователя в логи не попадают.
* Секреты (токен бота) задаются через `.env` и не попадают в репозиторий; взаимодействие с Telegram —
  через long polling.
* Сейчас доступ к боту ограничен whitelist'ом: бот отвечает только telegram-идентификаторам из `TELEGRAM_ALLOWED_IDS`
  (пустой список закрывает бота полностью).
* `/delete_all_data` — двухфазное удаление всего аккаунта: сначала пользователь передаёт владение или
  отзывает доступ по всем общим профилям, затем подтверждает словом «удалить»; весь план применяется
  атомарно одной транзакцией.
* Удаление профиля владельцем возможно только если в нём нет других участников; общие профили сначала
  передаются другому участнику либо доступ отзывается.
* **Права на записи:** любой участник профиля может добавлять/удалять/выгружать записи (симптомы, курсы, приёмы);
  действия с самим профилем (шеринг, передача владения, удаление) — только владелец. Доступ проверяется
  в момент операции (гард `ProfileAccessGuard`), при отзыве прав во время анкеты пользователь получает
  уведомление и возвращается на экран выбора профиля. Запись идёт под pessimistic lock: write-операции
  берут row-lock строки связи «пользователь-профиль» (`SELECT ... FOR UPDATE`), поэтому параллельный
  отзыв доступа или удаление профиля дожидаются завершения текущей записи. Отметка приёма резолвит
  курс с блокировкой его строки: параллельное удаление курса дожидается завершения приёма, а приём
  без привязки сохраняется только для уже удалённого курса.

## Архитектура

Проект разделён на четыре слоя:

* **domain** — сущности предметной области (`Profile`, `User`, `UserRole`, `ProfileInvite`,
  `MedicationCourse`, `SymptomLog`, `MedicationIntake`).
* **repository** — доступ к данным (Spring Data JDBC), Flyway-миграции.
* **service** — бизнес-логика, Telegram-free и юнит-тестируемая (`UserService`, `ProfileService`, `NotificationService`,
  `SymptomService`, `MedicationCourseService`,
  `IntakeService`, `ProfileAccessGuard`, `DailyPlanBuilder`, `LowStockAlertBuilder`).
* **telegram** — UI-слой бота. Общается только с сервисами (не с репозиториями):
    * `HealthTrackerBot` — тонкий: получает `Update` и передаёт в `UpdateHandler`.
    * `UpdateHandler` — интерфейс обработки входящего апдейта.
    * `PerChatUpdateHandler` — декоратор над `BotDispatcher` (режим по умолчанию): очередь на каждый чат,
      апдейты одного чата последовательны (виртуальный поток `task-chat-<id>`), разные чаты —
      параллельны. Отключается флагом `app.parallel.enabled=false`.
    * `BotDispatcher` — маршрутизирует ввод к командам по явным ключам (детерминированно);
      после клика уничтожает inline-клавиатуру сообщения (кнопки одноразовые);
      карты команд immutable, `awaitingInput` — потокобезопасный.
    * `command/*` — команды: старт, профили (выбор/создание/шеринг/управление), уведомления, приватность,
      помощь; `command/section/*` — разделы записей (симптомы, курсы, приёмы) на `AbstractSectionCommand`
      (меню, выгрузка, удаление по id, шапка «Профиль: имя»); `command/wizard/*` — визарды анкет (симптом,
      курс) на `AbstractWizardCommand` (шаги рефлексией из класса свойств, подтверждение/отмена кнопками);
      `command/intake/*` — флоу отметки приёма (не визард): `IntakeTakeCommand` + `IntakeFlowMarker`,
      шаги препарат → дозы → время → подтверждение.
    * `scheduler/NotificationScheduler` — ежедневная рассылка планов на сегодня (@Scheduled).
    * `screen/*` — переиспользуемые экраны (меню профиля, выбор профиля, уведомления).
    * `support/*` — `ReplySender` (единственная точка отправки ответов в Telegram), `KeyboardFactory`
      (reply- и inline-клавиатуры), `DailyPlanFormatter` (HTML-текст плана на сегодня), `BotTexts`,
      `Commands`, `ConfirmationWords`, `ErrorTexts` (все пользовательские тексты и токены).

### Паттерны

* **Command** — каждый вход (команда/кнопка) обрабатывается отдельным классом `BotCommand`;
  диспетчер хранит их в мап по ключу ввода — текст команды либо callback-действие (`BotDispatcher`) — и вызывает по
  ключу;
  методы интерфейса — no-op по умолчанию (ISP): команда реализует только используемые.
* **State** — текущее состояние диалога хранится в памяти (`BotDispatcher.awaitingInput`,
  потокобезопасная карта), экран (меню профиля / выбор профиля) выводится из доменного контекста (`active_profile_id`).
  Состояние живёт в маркерах флоу, а не в потоке: апдейты одного юзера
  обрабатываются разными потоками, но продолжают одну анкету.
* **Builder** — построение клавиатур и ответов через встроенные builder'ы Telegram API;
  сборка сущностей/DTO — средствами Lombok (`@Builder`).

### Параллелизм

Каждый чат обрабатывается в виртуальном потоке с собственной очередью: апдейты одного чата
последовательны, разные чаты — параллельно. Весь ввод передаётся в `PerChatUpdateHandler`.

Флаг `app.parallel.enabled=false` отключает параллелизм и возвращает синхронную обработку
напрямую `BotDispatcher`.

Для проверки параллелизма вживую есть временная демо-команда `/sleep` — она засыпает в потоке
своего чата, остальные чаты продолжают отвечать. Демо включается и отключается флагом
`app.demo.sleep.enabled` в `application.yaml` (длительность — `app.demo.sleep.seconds`).
Для сравнения: с `app.parallel.enabled=false` тот же `/sleep` блокирует все чаты.

## Карта переходов (стейт-машина)

Экран определяется доменным контекстом (выбран ли профиль) + текущим ожиданием ввода (в памяти).
Reply-панель (2×2) фиксированная: «Меню профиля», «Выбор профиля», «Уведомления», «Помощь».
Рисуется один раз на `/start` и экранами не перерисовывается — Telegram хранит её сам.

```
[/start]
   │
   ├─ профиль НЕ выбран ──► [ВЫБОР ПРОФИЛЯ]
   └─ профиль выбран ─────► [МЕНЮ ПРОФИЛЯ]

[ВЫБОР ПРОФИЛЯ]              (reply-панель 2×2)
   │  выбрать профиль          ──► отметить is_active в tr_user_profile ──► [МЕНЮ ПРОФИЛЯ]
   │  создать профиль          ──► ввод имени ──► создать+выбрать ──► [МЕНЮ ПРОФИЛЯ]
   │  добавить по коду         ──► ввод кода ──► claimInvite ──► связь MEMBER, is_active=false ──► (этот же экран)

[МЕНЮ ПРОФИЛЯ]               (reply-панель 2×2)
   │  управление профилем      ──► [УПРАВЛЕНИЕ ПРОФИЛЕМ] (кнопка только у владельца)
   │  симптомы/курсы/приёмы    ──► [РАЗДЕЛ ЗАПИСЕЙ] (любой участник профиля)
   │  (без профиля)            ──► переход в [ВЫБОР ПРОФИЛЯ]

[РАЗДЕЛ ЗАПИСЕЙ]             (симптомы / курсы / приёмы)
   │  добавить                 ──► визард анкеты (шаги → подтвердить/отменить) ──► [РАЗДЕЛ ЗАПИСЕЙ]
   │  отметить приём           ──► флоу отметки приёма (см. ниже) ──► [РАЗДЕЛ ЗАПИСЕЙ]
   │  выгрузить                ──► симптомы — за 7 дней; курсы — весь список + остаток доз;
   │                                приёмы — за 7 дней по дате приёма
   │  удалить                  ──► список записей кнопками по id ──► выбрать id ──► перерисовать список
   │  назад                    ──► [МЕНЮ ПРОФИЛЯ]
   │  (доступ отозван)         ──► «К профилю нет доступа» ──► [ВЫБОР ПРОФИЛЯ]

[ФЛОУ ОТМЕТКИ ПРИЁМА]        (состояние — IntakeFlowMarker)
   │  шаг 1 препарат — кнопки активных курсов или ручной ввод названия
   │  шаг 2 дозы — кнопки 1/2/«Пропустить» (1) или число
   │  шаг 3 время — «Сейчас» или ЧЧ:ММ / ДД.ММ ЧЧ:ММ
   │  шаг 4 подтверждение — подтвердить ──► сохранение (INSERT + счётчик доз; остаток в ответе,
   │                                         «⚠️ Не хватает доз» при перерасходе, дубль — «✅ Уже отмечено») ──► [РАЗДЕЛ ЗАПИСЕЙ]
   │  повторить ──► шаг 1; отменить ──► отмена ──► [РАЗДЕЛ ЗАПИСЕЙ]

[УПРАВЛЕНИЕ ПРОФИЛЕМ]         (только владелец; выход — инлайн-кнопка «↩️ Назад»)
   │  в меню профиля           ──► [МЕНЮ ПРОФИЛЯ]
   │  создать код приглашения  ──► создать код (8 симв., 72 ч, одноразовый) ──► показать ──► (этот же экран)
   │  переименовать            ──► ввод имени ──► переименовать ──► (этот же экран)
   │  отозвать доступ          ──► удалить связи MEMBER + неиспользованные коды ──► (этот же экран)
   │  передать владение        ──► список участников ──► выбрать участника ──► ввод слова «передать»
   │                           ──► передача ролей ──► [ВЫБОР ПРОФИЛЯ]
   │                           ──► любой другой текст ──► отмена ──► (этот же экран)
   │  удалить профиль          ──► ввод слова «удалить» ──► удалить ──► [ВЫБОР ПРОФИЛЯ]
   │                           ──► любой другой текст ──► отмена ──► (этот же экран)

[/delete_all_data]            (двухфазное атомарное удаление аккаунта)
   │  ──► предупреждение + классификация профилей
   │        • личные — будут удалены
   │        • member — выход из профиля
   │        • общие (владелец) — по одному меню: передать владение / отозвать доступ
   │  ──► после всех решений — сводка плана удаления
   │  ──► ввод слова «удалить» ──► один @Transactional (передачи/отзывы → каскад удаления)
   │  ──► любой другой текст ──► отмена, данные неизменны

[УВЕДОМЛЕНИЯ]                (доступен всегда)
   │  изменить время           ──► ввод ЧЧ:ММ ──► сохранить ──► [УВЕДОМЛЕНИЯ]
   │  отключить                ──► выключить рассылку плана ──► [УВЕДОМЛЕНИЯ]
   │  «План на сегодня»        ──► вывести план (тот же текст, что при рассылке; пометку
   │                                «отправлено» НЕ ставит) + кнопка «↩️ Назад» ──► [УВЕДОМЛЕНИЯ]
   │  (планировщик)            ──► запуск раз в минуту: поиск юзеров, ожидающих сейчас ежедневный план,
   │                                сборка и отправка плана по профилям
```

### Ожидание ввода

Одношаговые анкеты (имя профиля, время уведомлений, код приглашения, новое имя, слово подтверждения)
хранятся в памяти в `BotDispatcher.awaitingInput` под маркером флоу, который возвращает сама команда.
Контракт: `null` — анкета завершена, иначе ожидание продолжается под тем же маркером. Состояние живёт
в маркере, а не в потоке: апдейты одного юзера обрабатываются разными потоками, но продолжают одну
анкету. Любая навигация (reply-кнопки, другой callback) сразу снимает ожидание — флоу «умирает».

## Уведомления

### Сценарий 1 — ежедневный план «План на сегодня»

Раз в минуту (`NotificationScheduler`, cron `0 * * * * *`) выбираются пользователи, у которых
`notification_time` уже наступила, а на сегодня рассылка ещё не отправлялась (`last_notified_date` — дата последней
отправки, сравнение по дате, а не по времени).
Им высылается список активных на сегодня курсов по профилям (профиль на своей строке,
каждый курс — на своей); профили без активных курсов пропускаются.

Правила:

* Пометка `last_notified_date = today` ставится **после подтверждённой отправки**:
  доставка не подтверждена — пометки нет, следующий тик догонит (дубль возможен максимум для одного
  пользователя «в полёте», приоритет «дубль вместо потери»).
* Сбой в рассылке одного пользователя не влияет на остальных: обработка per-user, ошибка логируется
  и не роняет тик.
* Пустой день (нечего пить) — ничего не отправляем, но пользователя помечаем, иначе тик
  повторял бы запрос каждую минуту.
* При смене дня пометка «устаревает» сама собой (сравнение с текущей датой).
* Установка времени: если новое время ещё **впереди** — план придёт сегодня (пометка
  сбрасывается); если время уже **наступило** (в том числе ровно сейчас) — сегодня не шлём,
  начнём с завтрашнего дня.
* Ручная кнопка «📋 План на сегодня» в меню уведомлений показывает тот же текст без пометки
  пользователя — авто-рассылка в свой срок всё равно придёт.

### Сценарий 2 — «заканчивается лекарство»

При отметке приёма, если курс дойдёт до остатка «по нижней границе», близкой к нулю,
профиль участнику отправляется предупреждение. Порог: `dosesPerPackage − dosesTaken ≤ dosesPerDay` —
на день остаётся меньше, чем доз по норме (`dosesPerDay` отсутствует — порог 1).
Отправляется только при реальном пересечении с верхней зоны (остаток был больше порога),
повторный приём в той же зоне или перерасход молчат. Уведомление получают все участники
профиля, кроме того, кто отметил приём. Таблица уведомлений пока не вводится (YAGNI).

## База данных

| Таблица                | Назначение                                                                                                                                                                                                                                                                                                                                                                   |
|------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `t_users`              | пользователи (синтетический `id`, `telegram_id` — уникально; `telegram_username`, `telegram_first_name`, `notification_time`, `last_notified_date` — дата последней ежедневной рассылки, для дедупа «на сегодня уже отправлено»; частичный индекс `t_users_notification_due_idx` на `(notification_time, last_notified_date)` — под выборку due-пользователей)               |
| `t_profiles`           | профили (подопечные)                                                                                                                                                                                                                                                                                                                                                         |
| `tr_user_profile`      | связь пользователь ↔ профиль (роль OWNER/MEMBER, `is_active` — активный профиль; уникальный частичный индекс гарантирует один активный на пользователя)                                                                                                                                                                                                                      |
| `t_profile_invites`    | одноразовые коды приглашений (8 символов, TTL 72 ч, атомарный claim в `claimInvite`)                                                                                                                                                                                                                                                                                         |
| `t_symptom_logs`       | записи симптомов (jsonb `properties`: название, комментарий, `symptomTime`; недельная выгрузка — по `symptomTime`, по умолчанию `now`)                                                                                                                                                                                                                                       |
| `t_medication_courses` | курсы лечения (jsonb `properties`, `doses_taken` — счётчик принятых доз; остаток вычисляется как `max(0, dosesPerPackage − doses_taken)`, только при заданной упаковке)                                                                                                                                                                                                      |
| `t_medication_intakes` | приёмы лекарств (jsonb `properties`: препарат, `takenAt`, дозы; выборка за день/неделю — по `takenAt`, по умолчанию `now`; `course_id` — справочно, обнуляется при удалении курса через `ON DELETE SET NULL`; уникальный индекс `uq_med_intake_dedup` (профиль + курс/препарат + время) защищает от двойной отметки одного приёма, `takenAt` хранится с точностью до минуты) |

Миграции: `src/main/resources/db/migration`.
